# BMAD setup

How BMAD is installed and customized for this project, and what to carry over to a new workspace. Project rules (branching, spec first, the security gate, finishing a story) are in [CONTRIBUTING.md](CONTRIBUTING.md); this page is only about the BMAD tooling.

## Workspace layout

BMAD is installed in a folder **above** the app repo, so one BMAD install serves the repo and its git worktrees.

```text
<workspace>/               BMAD project root (not a git repository)
  _bmad/                   BMAD install; _bmad/custom/ holds every local change (this page)
  .claude/, .agents/       skills and agents generated by the installer
  .github/agents/          agent definitions generated by the installer
  .tea/                    Test Architect enforcement config (generated)
  little-steps/            the app repo (git); BMAD outputs live in its .specs/
  worktrees/               git worktrees, one per story in flight (sibling of the repo)
```

The BMAD root is not under version control, so **the files in `_bmad/custom/` exist nowhere else than on disk**. This page is their source of record: copy them from here into a new workspace.

## What we added (all in `_bmad/custom/`)

Upgrades never overwrite this folder. The base files say so: they are "overwritten on every update" and tell you to override in `_bmad/custom/` instead.

| File | Purpose |
|---|---|
| `config.toml` | Redirects BMAD outputs into the app repo and points project knowledge at the repo's `docs/` |
| `branch-local-outputs.md` | One rule: BMAD outputs travel with the story branch, with the status transitions |
| `bmad-build.toml`, `bmad-code-review.toml`, `bmad-retrospective.toml`, `bmad-sprint-planning.toml`, `bmad-correct-course.toml` | Load that rule into each skill that writes BMAD outputs |

`config.user.toml` is the personal, git-ignored layer and is empty.

### `config.toml`

Why: by default BMAD writes to `<workspace>/_bmad-output/`, outside the repo, so nothing is committed. This sends everything into the repo's `.specs/`, including the Test Architect outputs, which have their own settings. `project_knowledge` pointed at a `docs/` folder that does not exist at the BMAD root.

```toml
# Team / enterprise overrides for _bmad/config.toml.
# Keep major BMAD artifacts (PRD, UX, architecture, epics, stories, specs)
# inside the app repo so they are version-controlled.
[core]
output_folder = "{project-root}/little-steps/.specs"

[modules.bmm]
project_knowledge = "{project-root}/little-steps/docs"
planning_artifacts = "{project-root}/little-steps/.specs/planning-artifacts"
implementation_artifacts = "{project-root}/little-steps/.specs/implementation-artifacts"

# Keep Test Architect (TEA) outputs in the app repo too. The default is
# {project-root}/_bmad-output/test-artifacts, which is outside the repo.
# The *_output keys are relative to the project root.
[modules.tea]
test_artifacts = "{project-root}/little-steps/.specs/test-artifacts"
test_design_output = "little-steps/.specs/test-artifacts/test-design"
test_review_output = "little-steps/.specs/test-artifacts/test-reviews"
trace_output = "little-steps/.specs/test-artifacts/traceability"
```

If the app repo folder has a different name in another workspace, change `little-steps` in every path.

### `branch-local-outputs.md`

Why: BMAD's step files name `sprint-status.yaml` and the other outputs by an absolute path in the main checkout. On a story branch or worktree that edits a copy which never reaches the pull request, so statuses were left behind. BMAD also never sets a story to `done` by itself. This rule fixes both without editing BMAD.

```markdown
# BMAD outputs travel with the story branch

BMAD-managed outputs live in the app repo under `.specs/` (`implementation-artifacts/sprint-status.yaml`, `implementation-artifacts/deferred-work.md`, story spec files, retrospective files, planning artifacts). They are version-controlled, so they only reach `main` if they are committed on the story's branch.

## Where to read and write them

- Resolve the app repo root with `git rev-parse --show-toplevel` from the directory you are working in. Read and write every BMAD output at its path relative to that root (for example `<root>/.specs/implementation-artifacts/sprint-status.yaml`).
- Several workflow steps name these files by an absolute path or a config path that points at the main checkout. When you are in a branch or a git worktree, treat that as the same relative path under your own repo root instead. Never edit the main checkout's copy from a branch, and never skip a status sync because the named path is outside your worktree.
- Leave no BMAD output as an uncommitted change in another checkout.

## Status transitions (all in the story's branch, committed with it)

1. `in-progress`: when implementation starts. Also set the parent epic from `backlog` to `in-progress`.
2. `review`: when the story is handed over for validation.
3. `done`: when the user accepts the story, before the branch is pushed. In one commit set the spec's frontmatter `status` to `done`, the story to `done` in `sprint-status.yaml`, and `last_updated`. When every story of the epic is `done`, set the epic to `done`.
4. A story that is already at or past the target status is left alone.

## Before handing over or pushing

Check that the spec's `status` and the story's entry in `sprint-status.yaml` agree, that every deferred item has its line in `deferred-work.md`, and that `git status` shows no BMAD output left uncommitted. Fix any difference in the same branch.
```

### The five skill overrides

Four of them are identical. They load the rule above as a persistent fact for the whole run:

```toml
# Team override. BMAD outputs travel with the story branch: see branch-local-outputs.md.

[workflow]
persistent_facts = ["file:{project-root}/_bmad/custom/branch-local-outputs.md"]
```

Use that for `bmad-code-review.toml`, `bmad-retrospective.toml`, `bmad-sprint-planning.toml` and `bmad-correct-course.toml`. `bmad-build.toml` is the same plus a completion check:

```toml
# Team override. BMAD outputs travel with the story branch: see branch-local-outputs.md.

[workflow]
persistent_facts = ["file:{project-root}/_bmad/custom/branch-local-outputs.md"]

on_complete = "Before reporting, confirm that the story's entry in sprint-status.yaml under the current repo root is `review`, that it matches the spec's frontmatter status, and that no BMAD output is left uncommitted. When the user later accepts the story, run the `done` transition from branch-local-outputs.md before pushing."
```

## Setting up another workspace

1. Create the workspace folder and clone the app repo into it as `little-steps/`. Create the sibling `worktrees/` folder.
2. Install BMAD in the workspace folder (the parent of the repo) with the modules and versions above, targeting claude-code (and github-copilot if you use it).
3. Create `_bmad/custom/` and add the seven files from this page: `config.toml`, `branch-local-outputs.md` and the five skill overrides. Keep `config.user.toml` for personal settings.
4. In each git worktree you create for a story, link the scan tools the pre-commit hook needs (they install into the main checkout's `.tools/`, which a new worktree does not have) and keep the link out of git:

   ```bash
   ln -s <workspace>/little-steps/.tools <workspace>/worktrees/<story>/.tools
   echo ".tools" >> <workspace>/little-steps/.git/info/exclude
   ```

   The tools are installed once with `deploy/security-scan.sh install-tools` (see the README).
5. Verify (next section).

## Verify the setup

```bash
# the merged output paths should all point into little-steps/.specs
uv run _bmad/scripts/resolve_config.py --project-root <workspace> | grep -E "artifacts|_output|project_knowledge"

# each of the five skills should list branch-local-outputs.md under persistent_facts
for s in bmad-build bmad-code-review bmad-retrospective bmad-sprint-planning bmad-correct-course; do
  uv run _bmad/scripts/resolve_customization.py --skill .claude/skills/$s --project-root <workspace> --key workflow | grep -A1 persistent_facts
done
```

## After upgrading BMAD

The overrides survive an upgrade, but a silent change can stop one from applying. After every upgrade:

1. Confirm `_bmad/custom/` still has the seven files, and take a copy of it before you upgrade.
2. Re-run the two checks above.
3. If a field was renamed or a skill was renamed or split, update the override. A skill that starts writing `sprint-status.yaml` or `deferred-work.md` needs the same `persistent_facts` line.
4. On the next story, confirm the sprint status change appears in the pull request.

## Known limits

- The rule is an instruction the agent follows, not a mechanical check. If the `done` transition is missed, the spec and the sprint status will disagree, which the "before handing over" check is meant to catch.
- `_bmad/` is not version-controlled. Back it up, or move the workspace root under version control.
